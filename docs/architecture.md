# معماری

## اجزای برنامه

| برنامه | مسئولیت |
| --- | --- |
| account | کاربر سفارشی مبتنی بر تلفن، OTP، نشانی‌ها، حریم خصوصی |
| catalog | دسته‌ها، محصول‌ها، گونه‌ها، تصویرها، کنترل فایل و گردش انبار |
| commerce | سبد مهمان و کاربر، علاقه‌مندی، محاسبهٔ قیمت، کوپن، سفارش، رویدادها |
| payments | درخواست و تأیید زرین‌پال، تراکنش و ثبت دستی رسید بازپرداخت |
| storefront | تنظیمات فروشگاه، نرخ ارسال، محتوای صفحهٔ اصلی و ابزار مدیریت |

صفحه‌های عمومی و پنل مدیر با قالب‌های Django ارائه می‌شوند. منطق قیمت، رزرو موجودی، انتقال وضعیت و ارتباط‌های بیرونی در سرویس‌هاست تا ورودی مرورگر مرجع قیمت یا پرداخت نباشد.

## مسیر خرید

1. اقلام سبد از دیتابیس خوانده می‌شوند و قیمت و تخفیف دوباره در سرور محاسبه می‌شوند.
2. پیش‌نمایش قیمت با امضای Django به سبد، کاربر، نشانی، تعداد، قیمت‌ها و کد تخفیف متصل می‌شود.
3. هنگام ایجاد سفارش، سبد، محصول‌ها، گونه‌ها و کوپن قفل می‌شوند؛ امضا و موجودی دوباره بررسی می‌شود.
4. سفارش یک snapshot از نشانی و قیمت محصول دارد و موجودی تا پایان پنجرهٔ پرداخت رزرو می‌شود.
5. callback زرین‌پال فقط شروع بررسی است. وضعیت موفق فقط پس از verify سمت سرور ثبت می‌شود.
6. مبلغ نامنطبق یا پاسخ مبهم به وضعیت بررسی می‌رود؛ این سفارش خودکار برای آماده‌سازی آزاد نمی‌شود.
7. رویدادهای سفارش، تغییر انبار، اقدام مدیر و تطبیق رسید بازپرداخت ثبت می‌شوند.

## ذخیره‌سازی و حریم خصوصی

- تلفن در قالب بین‌المللی نرمال‌شده نگه‌داری می‌شود؛ OTP خام ذخیره نمی‌شود.
- snapshot نشانی در سفارش برای تاریخچه حفظ می‌شود.
- متن صفحه‌های محتوا escape می‌شود.
- فایل تصویر با امضای اولیهٔ فایل و سقف ۵ مگابایت بررسی می‌شود.
- تراکنش و رسید در admin فقط خواندنی‌اند؛ تغییر موجودی از فرم جداگانهٔ ثبت‌شونده انجام می‌شود.

## مرزهای یکپارچه‌سازی

Providerهای SMS و پرداخت با timeout محدود و پیام خطای پاک‌سازی‌شده اجرا می‌شوند؛ OTP، کلید، authority و پاسخ خام provider در پیام‌های کاربر ثبت نمی‌شوند. آزمون‌ها شبکه را mock می‌کنند.

واحد مبلغ ZarinPal در محیط پذیرنده باید تأیید شود. ضریب تبدیل از تنظیم ZARINPAL_TOMAN_TO_RIAL می‌آید؛ پیش‌فرض کد ۱۰ است، اما تا آزمون sandbox با پذیرندهٔ مربوطه نباید آن را فرض قطعی عملیاتی دانست.
